# הארכיטקטורה ההיברידית — Sheets + Apps Script + Firestore

> עודכן 16.9.2026, מול פריסה 131 וכללי אבטחה בני 486 שורות.
> **המסמך הזה הוא ה"איך בונים פונקציה חדשה".** הוא יושב בריפו ולא בזיכרון
> חיצוני בכוונה: זיכרון מפגר אחרי הקוד, קובץ שיושב ליד הקוד מתיישן איתו.
> אם משהו כאן לא מסכים עם הקוד — **הקוד צודק**, ויש לתקן כאן.

## 1. שלוש המערכות, ומה התפקיד של כל אחת

| מערכת | תפקיד | מי כותב | מי קורא |
|---|---|---|---|
| **Google Sheets** | מקור האמת לכל מידע אישי, ולכל מה שיועד עורך בעין | Apps Script בלבד | Apps Script בלבד |
| **Apps Script** | שער API, אכיפת הרשאות, מנוע תהליכים מתוזמנים | — | הדפדפן, דרך `doGet`/`doPost` |
| **Firestore** (Spark) | עותק קריאה מהיר לנתונים תפעוליים | Apps Script דרך חשבון שירות | **הדפדפן ישירות** |

**הכלל שמחזיק את הכול:** כל תחום חי במקום אחד בלבד. אין שיקוף דו-כיווני.
מה שעבר ל-Firestore — הגיליון הוא הגיבוי שלו, לא המקור המקביל שלו.

**למה Firestore בכלל:** נמדד בייצור (16.9) — קריאה ל-Apps Script עולה
**~2,000 אלפיות מינימום**, גם כשהיא מחזירה 120 בתים ולא נוגעת בגיליון. זו
התעוררות המנוע, ואי-אפשר לייעל אותה. קריאת Firestore מאותו דפדפן:
**24–163 אלפיות.** פי עשרים עד פי שמונים.

## 2. מה עבר, מה לא, ולמה

### עבר ל-Firestore
`gardenPlan` + `gardenMeta` · `services` · `budgetYears` · `budgetTx` ·
`counters` · `appConfig` (flags / rev / boot) · `gymStatus` · `gymCode` · `members` ·
`homeCounts` · `clubReservations` · `tourSteps` · `tourSeen`

> **צעד 12 (16.9) — עמוד הבית יוצא מ-Apps Script.** אחרי המונים נשארו שני
> דברים שהחזיקו את הקריאה: כרטיס הסיור והשריון הקרוב. `clubReservations`
> הוא **מסמך למשפחה** ונושא שלושה שדות בלבד (התחלה, סיום, סטטוס) —
> בלי אימייל ובלי ההערה החופשית של התושב; `tourSteps` הוא **מסמך לכל
> קהל** (`all` / `admins` / `perm-…`), כי קריאת אוסף שלם נדחית אם מסמך
> אחד בו אסור לקורא — Firestore אינו מסנן, הוא דוחה. ⚠️ **המדידה
> שהסבירה למה זה נדרש:** `rev` חוזרת *לפני* שער ההרשאות ולכן אינה
> קוראת את טאב התושבים; כל פעולה מאומתת משלמת קריאה מלאה שלו, ואי-אפשר
> להוריד אותה — רק לא לקרוא ל-Apps Script.

> **`homeCounts` (16.9)** — חמש תגיות הספירה של עמוד הבית, **מסמך
> לכל הרשאה** (`residents` / `gym` / `club` / `garden`). אין בו שום מידע
> אישי — רק מספרים. הפיצול הוא החלטת אבטחה: כלל פועל על
> מסמך שלם, ומסמך מאוחד היה נותן למנהל המכון גם את מספר
> בקשות ההרשמה הממתינות. המסמכים **מחושבים מחדש** (לא ±1):
> הספירה היא עמודה אחת, ומונה שסופר את עצמו סוטה בשקט מעריכה
> ידנית בגיליון. ⚠️ אין לו גיבוי, במכוון — הכול נגזר מהגיליון
> ונבנה מחדש כל שעה, בדיוק כמו `gymStatus`.

### נשאר בגיליון — **ולמה בדיוק**
הכלל של יועד: **מידע אישי לא עובר ל-Firestore.** אבל "יש עמודה אישית" אינו
סוף הדיון — יש דפוס מוכח לעקוף אותו (סעיף 4). לכן לכל תחום שנשאר צריך לומר
מה **בדיוק** עוצר אותו:

| תחום | מה עוצר | האם ניתן לפתרון? |
|---|---|---|
| תושבים, עץ הוועד, בקשות הרשמה/שינוי | שמות, טלפונים, אימיילים — **הם כל התוכן** | לא. אין מה לסנן. |
| מסך ניהול המכון | ת.ז., תאריך לידה, תשובות שאלון בריאות | לא, ובמכוון. |
| שריוני המועדון | אימייל ומזהה משפחה בכל שריון | חלקית — הספירה עברה (`homeCounts/club`) |
| עדכוני תקציב · יומן הערות | `נערך ע"י` ו`סיבה` בטקסט חופשי | לא — ירדו מהמטען לפי דרישה (16.9) |
| **גינון — דיווחים** | `שם מדווח`, `טלפון` | **כן — רשימת היתר + גשר `familyId`** |
| **גינון — משימות** | `עודכן על ידי`, `אושר על ידי` | **כן — רשימת היתר** |
| **גינון — יומן** | `מבצע` | **כן — רשימת היתר** |

> **מצב הגינון, לפרוטוקול:** מה שעבר בצעד 03 הוא `גינון — שגרה` בלבד —
> תוכנית העבודה, שאין בה שום עמודה אישית. `דיווחים`, `משימות` ו`יומן`
> עדיין עוברים דרך Apps Script. ר' `docs/TODO-garden-migration.md`.

## 3. איך בונים פונקציה חדשה — עץ ההחלטה

```
האם הנתון מכיל שם / טלפון / אימייל / ת.ז. / בריאות?
├── לא  →  Firestore. סעיף 4.
├── כן, וזה **כל** התוכן  →  נשאר ב-Apps Script. סעיף 6.
└── כן, אבל רק בכמה עמודות  →  Firestore עם **רשימת היתר**. סעיף 4.1.
```

שאלה שנייה, בלתי תלויה:

```
האם הדפדפן צריך לכתוב?
├── לא (הרוב המוחלט)  →  קריאה בלבד. הכלל: allow write: if false.
└── כן  →  זה מסלול נדיר. ר' budgetTx בכללים: rules עם hasOnly,
          מעבר חוקי בלבד, ודגל statusPending שטריגר שעתי מחיל.
          אין Cloud Functions בשכבה החינמית — זו תבנית "תיבת הדואר".
```

## 4. לבנות תחום חדש ב-Firestore — שמונה שלבים

### 4.1 להחליט מה נוסע — **רשימת היתר, לעולם לא רשימת חסימה**
```js
var X_FS_FIELDS = ['מזהה', 'סטטוס', 'תאריך'];   // כל מה שאינו כאן לא עובר
```
טאב בגיליון הוא מבנה פתוח. עם רשימת חסימה, עמודה שמישהו יוסיף מחר
(טלפון, הערה אישית) תיכתב ל-Firestore בלי ששורה אחת בקוד תשתנה.
**ולכתוב ליד כל שדה שהושמט למה** — זה מה שמונע ממישהו להחזיר אותו.

### 4.2 לבחור מזהה מסמך — הוא קובע מי יוכל לקרוא
כלל אבטחה פועל על **מסמך שלם**. אי-אפשר "לקרוא את המסמך חוץ מהשדה ההוא".
לכן חלוקת המסמכים היא החלטת פרטיות, לא החלטת ביצועים:

- `gymStatus/{uid}` — מנוי הוא של **אדם**. שני בני זוג חולקים `familyId`,
  ולכן מסמך לפי משפחה היה חושף לבן/בת הזוג את המנוי של השני.
- `budgetTx/{year}__{id}` + שדה `familyId` — תושב רואה את של משפחתו.
- `gymCode/{uid}` — נפרד מ-`gymStatus` **דווקא** כי כלל לא מסנן שדות.

### 4.3 לכתוב את פונקציית ההמרה — **נקודת המרה אחת**
```js
function xDoc_(row, id) {
  var doc = { id: id, schema: 1, updatedAt: new Date() };
  X_FS_FIELDS.forEach(function (k) { doc[k] = row[k] == null ? '' : row[k]; });
  return doc;
}
```
`Date` הופך אוטומטית ל-`timestampValue` (ר' `fsVal_` ב-Firestore.gs).
**נקודת המרה אחת** היא מה שמונע סטייה שקטה בין מה שהשרת שולח למה
שה-Firestore מחזיר.

### 4.4 לכתוב את הסנכרון — ו**לקחת את הנעילה**
```js
function xSyncAll_(ss) {
  var live = {}, items = [], out = { ok:false, wrote:0, deleted:0, skipped:0 };
  /* ... בונים items ... */
  fsWriteAll_('x', items, out, live);
  fsSweepOrphans_('x', live, out);     // ⚠️ מוחק כל מה שלא נכתב עכשיו
  out.ok = true; return out;
}
```
🔴 **כל פונקציה שעושה `fsWriteAll_` ואז `fsSweepOrphans_` חייבת לרוץ
בתוך `withSyncLock_`.** שתי ריצות חופפות הורסות זו את זו: הסחיפה של
הראשונה רצה אחרי שהשנייה כתבה, רואה מסמך שאינו ברשימה *שלה*, ומוחקת
אותו. **אין שגיאה** — יש מסמכים שנעלמו.

```js
// בנקודת השיגור (doGet/doPost), לא בתוך הפונקציה:
return json_(withSyncLock_('xSync', function () { return xSyncAll_(ss); }));
```
⚠️ אם הפונקציה כבר לוקחת `LockService` בעצמה — לעטוף **מחוץ** לה
(ר' `saveServices_`/`saveServicesRun_`). תפיסה מקוננת של נעילת הסקריפט
באותה ריצה היא הדרך להיתקע.

### 4.5 לכתוב את כלל האבטחה — **לעולם לא רחב מהשרת**
זו הנקודה המסוכנת ביותר בסטאק. טעות כאן אינה קוד שנשבר אלא **נתונים
שנחשפים בשקט**.

```js
function canSeeX(uid) {
  return isMember() && m().isExternal == false && request.auth.uid == uid;
}
match /x/{uid} {
  allow read: if canSeeX(uid);
  allow write: if false;
}
```
חמישה כללי ברזל:
1. **`isMember()` ולא `signedIn()`.** `isMember()` דורש `active == true` —
   זה מתג הכיבוי של מי שסומן "עזב". כלל שמסתפק ב-`signedIn()` נותן
   למי שעזב את השיכון להמשיך לקרוא. (נתפס ב-`gymCode` יום לפני פרסום.)
2. **`isExternal == false`** — `authorize_` חוסם משתמש חיצוני מכל פעולה
   שאינה גינון. `== false` ולא `!= true`: שדה חסר חייב להיכשל-סגור.
3. **תנאי בפונקציה בעלת שם**, לא פרוש בתוך ה-`match`. יש בדיקה שאוכפת.
4. **מזהים בשפת הכללים חייבים להיות ASCII.** שדה עברי נקרא בסוגריים
   מרובעים: `resource.data['סטטוס']`. גישה בנקודה היא שגיאת פרסור
   שמפילה את פרסום הכללים **כולו**.
5. **ברירת המחדל `match /{document=**}` נשארת אחרונה.** ב-Firestore כל
   `match` שמתאים מעניק גישה — ולכן כלל **צר** יותר על מסמך ספציפי
   **אינו** מבטל wildcard שמעליו. להצר = להסיר את הנתון, לא להוסיף כלל.

### 4.6 לקרוא בלקוח — עם נפילה לאחור
```js
CBA.data.fsFirstRead("xFromFirestore", X_FROM_FIRESTORE, load, sheets, cb);
```
🔴 **ברירת המחדל בקוד חייבת להיות `true`** כשמשתמשים ב-`fsFirstRead`:
היא מקצרת על הקבוע לפני שהיא בודקת את הדגל החי, ולכן `false` הופך את
הדגל לחסר משמעות. הקבוע הוא **ברירת המחדל שמועברת ל-`flag()`**, לא שער.
כל כשל — אין SDK, אין משתמש, אין מסמך, אין הרשאה — נופל למסלול
Apps Script בלי שגיאה למשתמש.

### 4.7 להוסיף דגל — וקריאה וכתיבה מתהפכות **יחד**
```js
var FLAG_KEYS = [..., 'xFromFirestore'];   // Code.gs — הרשימה סגורה
```
🔴 אם התחום כולל גם כתיבה — **דגל אחד לשניהם.** קריאה וכתיבה שמתהפכות
בזמנים שונים = נתון שנכתב למקום אחד בזמן שקוראים מהשני, ונעלם מהמסך.
נתפס חי ב-15.9. הפתרון: השרת שולח את מצב הדגל במטען (`txFsOn`),
ושני הצדדים קוראים את אותו אות.

⚠️ **דגל שלא נכתב מעולם אינו במסמך** — `flagsSet_` שומר רק מפתחות
שמישהו שינה, ומפתח חסר פירושו ברירת המחדל שבקוד. מסך "מצב המערכת"
מחשב מצב **אפקטיבי**; אם מוסיפים דגל, להוסיף לו שם תיאור וברירת מחדל,
ויש בדיקה שמצליבה אותה מול הקבוע האמיתי.

### 4.8 לרשום את המסך ברישום התחומים
```js
var SCREEN_DOMAINS = { ..., xScreen: ["x"] };   // js/app.js
```
בלי זה, מחיקה שנעשתה במכשיר אחר לא תגרום למסך הפתוח להתרענן.

## 5. שני אילוצים שמעצבים כל תכנון

### 5.1 אין אינדקס מורכב
אימות דו-שלבי על `gizbar30` חוסם את קונסולת Google Cloud, ולכן **אי-אפשר
ליצור אינדקס מורכב**. כל שאילתה חייבת להיות **שאילתת שוויון בלבד** —
בלי מיון ובלי אי-שוויון — כי רק אלה נשרתות מהאינדקסים האוטומטיים
(מיזוג זיגזג). זו הסיבה ש-`budgetTx` הוא מסמך לכל תנועה עם `year`
ו-`familyId` כשדות שוויון. **אל תוסיף `orderBy` — השאילתה תיפול בייצור.**

### 5.2 אין Cloud Functions (Spark, בלי כרטיס אשראי)
אין טריגר שרץ על כתיבה ל-Firestore. כתיבה מהדפדפן מוחלת על הגיליון
בתבנית **"תיבת דואר"**: הדפדפן כותב עם `statusPending: true`, והעבודה
השעתית (`budgetTxApplyPending_`) מחילה. המשמעות: החלה מתעכבת עד שעה,
והנעילה (`withSyncLock_`) היא **מייעצת** ולא טרנזקציונית.

מכסות Spark: 50,000 קריאות ליום, ~20,000 כתיבות. כל `get()` **בתוך כלל**
נספר גם הוא.

## 6. מתי **לא** להעביר, ומה לעשות במקום
לפני שמעבירים תחום — לשאול אם בכלל צריך. שתי חלופות זולות בהרבה:

1. **לספור בעמודה אחת במקום למשוך שורות.** `countStatus_` — אם הלקוח
   צורך מספר אחד, אין סיבה לשלוח לו שורות. חסך ~3 שניות ו-9KB בעמוד
   הבית, והוריד מהחוט ת.ז. ותשובות שאלון בריאות.
2. **לאחד קריאות.** `homeExtras` מאחדת שש קריאות לאחת וחוסכת חמש
   רצפות של שתי שניות. ⚠️ אבל לבדוק שאין בתוכה קריאה כפולה לאותו
   מקור — היא קראה את יומן Google פעמיים (תוקן 16.9 — `clubWindowEvents_`).
3. **להוציא מהמטען מה שנצרך במסך אחד.** שני היומנים של התקציב
   (`budgetLogs`, 16.9) — בלי מיגרציה, בלי כלל חדש, ובלי להזיז טקסט
   חופשי ושם של עורך. ⚠️ סדר הדיפלוי הפוך — **לקוח קודם**, כי
   השרת מפסיק לשלוח משהו שהלקוח עדיין צריך.

## 7. איך בודקים שזה עובד
- **מסך "מצב המערכת"** (מנהל-על, אריח בתפריט המשתמש) — מדליק ומכבה כל
  דגל, ומריץ קריאת Firestore **אמיתית מהדפדפן** לכל מסמך מרכזי עם
  מדידת זמן. 🔴 הבדיקה חייבת לרוץ שם ולא בשרת: כללי האבטחה נאכפים על
  הקורא, ו-Apps Script עוקף אותם דרך חשבון שירות — בדיקה שרצה בשרת
  מצליחה **תמיד**.
- **`tools/`** — 42 מארזי בדיקה, ~1,914 בדיקות. `npm install` בתיקייה
  פעם אחת בכל מכונה חדשה (jsdom).
- לכל תחום חדש: מארז שבודק את רשימת ההיתר, את הכלל, ואת הנפילה לאחור.

## 8. סדר הפריסה — **ארבעה שערים, לא שלושה**
1. **Push** ל-GitHub (לקוח). חייב `?v=` חדש ב-`index.html` **וב-**`service-worker.js`.
2. **Apps Script** — לפריסה → ניהול הפריסות → **עיפרון** → גרסה חדשה → לפריסה.
   לעולם לא "פריסה חדשה" מהתפריט — זה יוצר URL חדש ושובר את האפליקציה.
   ⚠️ **השמירה בעורך נכשלת בשקט** (נתפס 16.9): `Cmd+S` דרך מקלדת
   סינתטית מפסיק לעבוד אחרי שהדף פתוח זמן מה — הכותרת ממשיכה להציג
   "שינויים שלא נשמרו", ורענון מחזיר את הקוד הישן. מה שכן עובד:
   לשגר `KeyboardEvent('keydown',{key:'s',metaKey:true,bubbles:true})`
   אל `document`. **והאימות היחיד שסופר הוא רענון מלא והשוואת אורך
   מול raw.githubusercontent** — לא הכותרת.
3. **כללי Firestore** — פרסום מקונסולת Firebase.
4. **זריעה ואז הדלקה** — להריץ את פונקציית הסנכרון פעם אחת, לוודא
   שהמסמכים קיימים ונקראים, **ורק אז** להדליק את הדגל.

⚠️ הסדר אינו שרירותי: דגל שנדלק לפני שהמסמכים קיימים נותן מסך ריק.

# 8. 🔴🔴 ההיפוך — כשה-Firestore הופך למסד החי (16.9.2026, הגינון)

עד כאן המסמך מתאר דפוס אחד: **הגיליון הוא המקור, Firestore הוא

המועדף לתחום אינטראקטיבי.

## 8.1 מה הוביל לזה — ושווה להבין את השאלה, לא רק את התשובה

יועד שאל: *"אני לא מבין למה אנחנו נשארים עם פערים של עדכון פעם
בשעה, Firestore אמור לתת לנו רענון זמן אמת."*

**והתשובה שלי הייתה לא מדויקת בהתחלה.** Firestore **כן** נותן זמן
אמת. הבעיה מעולם לא הייתה הקצב שלו אלא **מי כותב למסמך**: כשהגיליון
הוא המקור, מסמך מתעדכן רק כשמישהו מסנכרן אותו. דחיפה מיידית של מסמך
שאף אחד לא עדכן — דוחפת כלום.

🔑 **המסקנה:** "לרענן מהר יותר" הוא תיקון לתסמין. **התיקון הוא שמי
שמשנה את הנתון יכתוב אותו למקום שממנו קוראים.**

## 8.2 מה עבר בפועל

| | לפני | אחרי |
|---|---|---|
| דיווח תושב | Apps Script → גיליון → סנכרון | **הדפדפן כותב ל-Firestore** |

## 8.3 מה נשאר ב-Apps Script — ולמה דווקא זה

**שני דברים שהוא היחיד שיודע לעשות:**
1. **העלאת תמונות ל-Drive** — אין Firebase Storage בתוכנית החינמית.
2. **שליחת מיילים** — אין Cloud Functions.

שניהם **שגר-ושכח**: הדפדפן כותב את המסמך, ואז קורא להם בלי להמתין.

**ודבר שלישי, שהוא החלטה ולא אילוץ:** עשר פעולות הניהול של המשימות
נשארו בשרת. הן מחזיקות לוגיקה עסקית שכלל אבטחה **אינו יודע לאכוף** —
"חובה לכתוב מה נעשה לפני סגירת תקלת תושב", "אפשר לבטל רק בתוך חלון
הערעור". כלל יודע לאכוף **מי** כותב ו**מה צורת** המסמך, לא את אלה.
⚠️ מה שרץ בדפדפן אפשר לעקוף. לוגיקה שקובעת מה מותר — לא שם.

## 8.4 שלושת הדפוסים שההיפוך הוסיף

### א. מונה במקום ספירה
מזהה רץ שהמשתמש רואה ("דיווח מספר 7") לא יכול להיספר בגיליון כשהדפדפן
כותב. `counters/{id}` + `runTransaction` — אטומי. הכלל מתיר **קידום
באחד בלבד**, והנזק הגרוע האפשרי הוא מספר שרוף ברצף.

### ב. תיבת דואר לכל מה שדורש שרת
הדפדפן מרים דגל במסמך (`mailPending: true`) וקורא לשרת בלי להמתין.
אם הקריאה נפלה — **סריקה שעתית על שאילתת שוויון** תופסת. השרת מוריד
את הדגל, ולכן זה אידמפוטנטי ולא שולח פעמיים.

### ג. פער שהופך לנתון במקום להיבלע
תמונה שנכשלה הייתה נבלעת ב-`catch` שקט. עכשיו המסמך נושא **כמה
נשלחו מול כמה נחתו**, והפער נראה בשלושה מקומות: התושב, המנהל,
וסריקה שעתית שמתריעה פעם אחת לכל דיווח.

⚠️ **התמונות עולות אחת-אחת** — וזה גם מה שנותן אחוז אמיתי בלי מאזין
על `xhr.upload`, שאסור מול Apps Script (ר' 5.2 והבדיקה שמונעת אותו).

## 8.5 🔴 שני לקחים מהאימות בייצור — שניהם עלו אחרי שהבדיקות היו ירוקות

**1. הבדיקות אימתו את מה שתכננתי, לא את מה ששכחתי.**
הצוות האדום מצא ש-`canSeeGardenReport` נכתב **בלי בדיקת חיצוניות**,
בעוד שהשרת חוסם משתמש חיצוני מכל `need` שאינו `PERM_GARDEN`. כלומר
הכלל היה **רחב מהשרת** — הדבר האחד שאסור. הנזק היה קטן (הוא היה
קורא את הדיווחים של הבית שלו), וזו בדיוק הסיבה שקל לפטור אותו.
**האינווריאנטה היא הנכס, לא המקרה הפרטי.**

**2. השוואת ספירות תפסה באג ש-2,400 בדיקות לא יכלו לתפוס.**
לפני ההדלקה השוויתי כמה שורות מחזיר כל מסלול: **41 מול 10**.
המיגרציה סיננה משימות לפי 'שנת תקציב', השנה התחלפה, ו-31 משימות
פתוחות נשארו בחוץ. המנהל היה מאבד את רוב תור העבודה בלי שגיאה.
הבדיקות רצות על גיליון מזויף שבו כל שורה נושאת שנה — הן **לא
יכלו** לראות את זה.

🔑 **הכלל שנולד מזה:** לפני הדלקת דגל, **להשוות ספירות בין שני
המסלולים**. לא "האם זה עובד" אלא "האם זה מחזיר את אותו מספר".

🔑 **ולקח תכנוני:** הרלוונטיות של משימה היא השבוע והסגירה שלה, לא
תווית שנת התקציב. מסנן שהועתק מתחום אחר בלי לשאול "מה הופך פריט
כאן לרלוונטי" הוא מסנן שגוי.

## הגשר שיודע לכתוב ולא יודע למחוק (16.9.2026)

יועד מחק משימת גינון שלוש פעמים. בכל פעם כתוב "נמחקה", ובכל פעם
המשימה חזרה. שלושה באגים התגלו מאותה נקודה, וכולם נולדו מאותו צעד:
מסך הניהול עבר לקרוא מ-Firestore בעוד שהכתיבה נשארה ב-Apps Script.

**1. `gardenAfterWrite_` היה upsert בלבד.**
`gardenTaskSyncSome_` סורקת את הטאב ומעתיקה את השורות שמצאה. אחרי
מחיקה אין שורה — הלולאה מחזירה 0, והמסמך ב-Firestore נשאר חי.
הגיליון נקי, השרת מחזיר `ok:true`, והמסך נבנה מהעותק.

🔑 **הכלל שנולד מזה:** *הוק סנכרון חייב לענות על שלוש שאלות, לא על
אחת.* "מה השתנה" זה החלק הקל. "מה נעלם" ו"מה נוצר בלי שאיש ביקש"
הם החלקים שנשכחים — ושניהם שקטים.
פעולה שמוחקת שורה מחזירה `deletedTaskIds` / `deletedReportIds`,
והגשר מוחק אותם לפני הסנכרון ומחריג אותם ממנו.

**2. שתי הפעולות שנשמטו ישבו שתי שורות מתחת לשש שלא.**
בנתב, `gardenTaskDelete` ו-`gardenReportDelete` נשארו חשופות בדיוק
מתחת לשש הפעולות שכן עטופות. הוק שיושב בנתב הוא הבחירה הנכונה —
אבל **רשימת ה-`case` היא עכשיו קוד קריטי**, ושורה שנשמטת ממנה
לא מייצרת שום שגיאה.

**3. `gardenMaterializeWeek_` התייתמה בלי שאיש שם לב.**
הפונקציה שיוצרת את משימות השגרה נקראה ממקום אחד: בתוך
`handleGardenTasks_`. ברגע שהמסך הפסיק לעבור שם, **אף אחד לא קרא
לה** — ומשימות השגרה של השבוע הבא פשוט לא היו נוצרות. זה לא מתקן
את עצמו ולא מתגלה עד שהשבוע מתחלף. עבר לטריגר השעתי.

🔑 **הכלל הכללי:** *כשמעבירים מסך ממסלול קריאה אחד לאחר, לבדוק מה
עוד היה תלוי בקריאה הישנה.* קריאה אינה רק קריאה — תופעות לוואי
שהתחבאו בתוכה מתות בשקט.

**4. `gardenLog` נקרא מאוסף שאיש לא כותב אליו.**
הלקוח שאל את Firestore על היומן. אין בשרת שום כתיבה לאוסף הזה.
ורשימה ריקה **אינה שגיאה**, ולכן `fsFirstRead` לא נפלה לאחור
והמסך פשוט הציג היסטוריה ריקה.

⚠️ **ובנוסף — לא היה אפשר לכבות את זה.** `fsFirstRead` בונה את שם
הדגל מהמפתח, וכאן נוצר `gardenLogFromFirestore` שאינו ב-`FLAG_KEYS`.
`flag()` על מפתח לא מוכר מחזיר את ברירת המחדל שבקוד.

🔑 **שני כללים:** *אוסף חדש נקרא רק אחרי שמוכח שמישהו כותב אליו*,
ו*כל מפתח `fsFirstRead` חייב דגל תואם ב-`FLAG_KEYS`* — אחרת נוצר
מסלול קריאה בלי מתג כיבוי.

**5. איפה נמדדת בדיקה של סנכרון.**
`gardenTaskDelete_` החזירה `ok:true` גם כשהבאג היה חי, וזו הסיבה
שהוא לא נתפס. `tools/test-garden-delete-firestore.js` מודד **אילו
קריאות DELETE יצאו ל-Firestore**, לא מה השרת החזיר. הגיליון המזויף
שם מוחק שורות באמת — בלי זה הבדיקה לא הייתה נוגעת בבאג.

## יצירה היא הצד השני של אותו מטבע (16.9.2026)

`gardenCreateTask_` מחזירה `{ok:true, id:<חדש>}`. `gardenAfterWrite_`
חיפש את המזהה ב-`res.taskId` ו-ב-`body.id` — ובבקשת יצירה אין אף אחד
מהם. כלומר משימה שמנהל פותח ידנית נכתבה לגיליון, שלחה מייל, ו**לא
הופיעה במסך** עד הסנכרון השעתי.

🔑 **המסקנה החוזרת:** הוק שמקבל `res` ו-`body` גנריים צריך **מיפוי
מפורש לכל פעולה**, ורשימת המיפויים היא קוד קריטי בדיוק כמו רשימת
ה-`case` בנתב. שם שדה שמשתנה בין פעולה לפעולה (`id` מול `taskId`)
הוא בדיוק המקום שבו הוק כזה נשבר בשקט.

## מזהה כפול הוא באג רק אחרי המעבר ל-Firestore (16.9.2026)

`gardenMaterializeWeek_` קראה `nextGardenId_` פעם אחת ולא נעלה. שתי
ריצות חופפות הקצו את אותו מספר. **בגיליון זה נראה כמו שתי שורות
מכוערות ותו לא** — האפליקציה הציגה את שתיהן.

ב-Firestore המזהה הוא שם המסמך. השנייה דורסת את הראשונה, ומשימה
אמיתית נעלמת מהמסך בלי שום שגיאה. נמצאו בייצור מזהים 12 ו-37.

🔑 **הכלל:** *כל טאב שהופך לאוסף חייב מזהה ייחודי מובטח.* לפני מעבר
תחום — להשוות `count(rows)` מול `count(unique ids)`. אם הם לא שווים,
המעבר ימחק נתונים בשקט.
