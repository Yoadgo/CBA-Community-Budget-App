## 1. שלוש המערכות, ומה התפקיד של כל אחת

| מערכת | תפקיד | מי כותב | מי קורא |
|---|---|---|---|
| **Google Sheets** | מקור האמת לכל מידע אישי, ולכל מה שיועד עורך בעין | Apps Script בלבד | Apps Script בלבד |
| **Apps Script** | שער API, אכיפת הרשאות, מנוע תהליכים מתוזמנים | — | הדפדפן, דרך `doGet`/`doPost` |
| **Firestore** (Spark) | עותק קריאה מהיר לנתונים תפעוליים | Apps Script דרך חשבון שירות | **הדפדפן ישירות** |

**הכלל שמחזיק את הכול:** כל תחום חי במקום אחד בלבד. אין שיקוף דו-כיווני.
מה שעבר ל-Firestore — הגיליון הוא הגיבוי שלו, לא המקור המקביל שלו.

**למה Firestore בכלל:** נמדד בייצור (16.9) — קריאה ל-Apps Script עולה
**~2,000 אלפיות מינימום**, גם כשהיא מחזירה 120 בתים ולא נוגעת בגיליון. זו
התעוררות המנוע, ואי-אפשר לייעל אותה. קריאת Firestore מאותו דפדפן:
**24–163 אלפיות.** פי עשרים עד פי שמונים.

## 2. מה עבר, מה לא, ולמה

### עבר ל-Firestore
`gardenPlan` + `gardenMeta` · `services` · `budgetYears` · `budgetTx` ·
`counters` · `appConfig` (flags / rev / boot) · `gymStatus` · `gymCode` · `members`

### נשאר בגיליון — **ולמה בדיוק**
הכלל של יועד: **מידע אישי לא עובר ל-Firestore.** אבל "יש עמודה אישית" אינו
סוף הדיון — יש דפוס מוכח לעקוף אותו (סעיף 4). לכן לכל תחום שנשאר צריך לומר
מה **בדיוק** עוצר אותו:

| תחום | מה עוצר | האם ניתן לפתרון? |
|---|---|---|
| תושבים, עץ הוועד, בקשות הרשמה/שינוי | שמות, טלפונים, אימיילים — **הם כל התוכן** | לא. אין מה לסנן. |
| מסך ניהול המכון | ת.ז., תאריך לידה, תשובות שאלון בריאות | לא, ובמכוון. |
| שריוני המועדון | אימייל ומזהה משפחה בכל שריון | חלקית — ספירה בלבד כבר עברה |
| **גינון — דיווחים** | `שם מדווח`, `טלפון` | **כן — רשימת היתר + גשר `familyId`** |
| **גינון — משימות** | `עודכן על ידי`, `אושר על ידי` | **כן — רשימת היתר** |
| **גינון — יומן** | `מבצע` | **כן — רשימת היתר** |

> **מצב הגינון, לפרוטוקול:** מה שעבר בצעד 03 הוא `גינון — שגרה` בלבד —
> תוכנית העבודה, שאין בה שום עמודה אישית. `דיווחים`, `משימות` ו`יומן`
> עדיין עוברים דרך Apps Script. ר' `docs/TODO-garden-migration.md`.

## 3. איך בונים פונקציה חדשה — עץ ההחלטה

```
האם הנתון מכיל שם / טלפון / אימייל / ת.ז. / בריאות?
├── לא  →  Firestore. סעיף 4.
├── כן, וזה **כל** התוכן  →  נשאר ב-Apps Script. סעיף 6.
└── כן, אבל רק בכמה עמודות  →  Firestore עם **רשימת היתר**. סעיף 4.1.
```

שאלה שנייה, בלתי תלויה:

```
האם הדפדפן צריך לכתוב?
├── לא (הרוב המוחלט)  →  קריאה בלבד. הכלל: allow write: if false.
└── כן  →  זה מסלול נדיר. ר' budgetTx בכללים: rules עם hasOnly,
          מעבר חוקי בלבד, ודגל statusPending שטריגר שעתי מחיל.
          אין Cloud Functions בשכבה החינמית — זו תבנית "תיבת הדואר".
```

## 4. לבנות תחום חדש ב-Firestore — שמונה שלבים

### 4.1 להחליט מה נוסע — **רשימת היתר, לעולם לא רשימת חסימה**
```js
var X_FS_FIELDS = ['מזהה', 'סטטוס', 'תאריך'];   // כל מה שאינו כאן לא עובר
```
טאב בגיליון הוא מבנה פתוח. עם רשימת חסימה, עמודה שמישהו יוסיף מחר
(טלפון, הערה אישית) תיכתב ל-Firestore בלי ששורה אחת בקוד תשתנה.
**ולכתוב ליד כל שדה שהושמט למה** — זה מה שמונע ממישהו להחזיר אותו.

### 4.2 לבחור מזהה מסמך — הוא קובע מי יוכל לקרוא
כלל אבטחה פועל על **מסמך שלם**. אי-אפשר "לקרוא את המסמך חוץ מהשדה ההוא".
לכן חלוקת המסמכים היא החלטת פרטיות, לא החלטת ביצועים:

- `gymStatus/{uid}` — מנוי הוא של **אדם**. שני בני זוג חולקים `familyId`,
  ולכן מסמך לפי משפחה היה חושף לבן/בת הזוג את המנוי של השני.
- `budgetTx/{year}__{id}` + שדה `familyId` — תושב רואה את של משפחתו.
- `gymCode/{uid}` — נפרד מ-`gymStatus` **דווקא** כי כלל לא מסנן שדות.

### 4.3 לכתוב את פונקציית ההמרה — **נקודת המרה אחת**
```js
function xDoc_(row, id) {
  var doc = { id: id, schema: 1, updatedAt: new Date() };
  X_FS_FIELDS.forEach(function (k) { doc[k] = row[k] == null ? '' : row[k]; });
  return doc;
}
```
`Date` הופך אוטומטית ל-`timestampValue` (ר' `fsVal_` ב-Firestore.gs).
**נקודת המרה אחת** היא מה שמונע סטייה שקטה בין מה שהשרת שולח למה
שה-Firestore מחזיר.

### 4.4 לכתוב את הסנכרון — ו**לקחת את הנעילה**
```js
function xSyncAll_(ss) {
  var live = {}, items = [], out = { ok:false, wrote:0, deleted:0, skipped:0 };
  /* ... בונים items ... */
  fsWriteAll_('x', items, out, live);
  fsSweepOrphans_('x', live, out);     // ⚠️ מוחק כל מה שלא נכתב עכשיו
  out.ok = true; return out;
}
```
🔴 **כל פונקציה שעושה `fsWriteAll_` ואז `fsSweepOrphans_` חייבת לרוץ
בתוך `withSyncLock_`.** שתי ריצות חופפות הורסות זו את זו: הסחיפה של
הראשונה רצה אחרי שהשנייה כתבה, רואה מסמך שאינו ברשימה *שלה*, ומוחקת
אותו. **אין שגיאה** — יש מסמכים שנעלמו.

```js
// בנקודת השיגור (doGet/doPost), לא בתוך הפונקציה:
return json_(withSyncLock_('xSync', function () { return xSyncAll_(ss); }));
```
⚠️ אם הפונקציה כבר לוקחת `LockService` בעצמה — לעטוף **מחוץ** לה
(ר' `saveServices_`/`saveServicesRun_`). תפיסה מקוננת של נעילת הסקריפט
באותה ריצה היא הדרך להיתקע.

### 4.5 לכתוב את כלל האבטחה — **לעולם לא רחב מהשרת**
זו הנקודה המסוכנת ביותר בסטאק. טעות כאן אינה קוד שנשבר אלא **נתונים
שנחשפים בשקט**.

```js
function canSeeX(uid) {
  return isMember() && m().isExternal == false && request.auth.uid == uid;
}
match /x/{uid} {
  allow read: if canSeeX(uid);
  allow write: if false;
}
```
חמישה כללי ברזל:
1. **`isMember()` ולא `signedIn()`.** `isMember()` דורש `active == true` —
   זה מתג הכיבוי של מי שסומן "עזב". כלל שמסתפק ב-`signedIn()` נותן
   למי שעזב את השיכון להמשיך לקרוא. (נתפס ב-`gymCode` יום לפני פרסום.)
2. **`isExternal == false`** — `authorize_` חוסם משתמש חיצוני מכל פעולה
   שאינה גינון. `== false` ולא `!= true`: שדה חסר חייב להיכשל-סגור.
3. **תנאי בפונקציה בעלת שם**, לא פרוש בתוך ה-`match`. יש בדיקה שאוכפת.
4. **מזהים בשפת הכללים חייבים להיות ASCII.** שדה עברי נקרא בסוגריים
   מרובעים: `resource.data['סטטוס']`. גישה בנקודה היא שגיאת פרסור
   שמפילה את פרסום הכללים **כולו**.
5. **ברירת המחדל `match /{document=**}` נשארת אחרונה.** ב-Firestore כל
   `match` שמתאים מעניק גישה — ולכן כלל **צר** יותר על מסמך ספציפי
   **אינו** מבטל wildcard שמעליו. להצר = להסיר את הנתון, לא להוסיף כלל.

### 4.6 לקרוא בלקוח — עם נפילה לאחור
```js
CBA.data.fsFirstRead("xFromFirestore", X_FROM_FIRESTORE, load, sheets, cb);
```
🔴 **ברירת המחדל בקוד חייבת להיות `true`** כשמשתמשים ב-`fsFirstRead`:
היא מקצרת על הקבוע לפני שהיא בודקת את הדגל החי, ולכן `false` הופך את
הדגל לחסר משמעות. הקבוע הוא **ברירת המחדל שמועברת ל-`flag()`**, לא שער.
כל כשל — אין SDK, אין משתמש, אין מסמך, אין הרשאה — נופל למסלול
Apps Script בלי שגיאה למשתמש.

### 4.7 להוסיף דגל — וקריאה וכתיבה מתהפכות **יחד**
```js
var FLAG_KEYS = [..., 'xFromFirestore'];   // Code.gs — הרשימה סגורה
```
🔴 אם התחום כולל גם כתיבה — **דגל אחד לשניהם.** קריאה וכתיבה שמתהפכות
בזמנים שונים = נתון שנכתב למקום אחד בזמן שקוראים מהשני, ונעלם מהמסך.
נתפס חי ב-15.9. הפתרון: השרת שולח את מצב הדגל במטען (`txFsOn`),
ושני הצדדים קוראים את אותו אות.

⚠️ **דגל שלא נכתב מעולם אינו במסמך** — `flagsSet_` שומר רק מפתחות
שמישהו שינה, ומפתח חסר פירושו ברירת המחדל שבקוד. מסך "מצב המערכת"
מחשב מצב **אפקטיבי**; אם מוסיפים דגל, להוסיף לו שם תיאור וברירת מחדל,
ויש בדיקה שמצליבה אותה מול הקבוע האמיתי.

### 4.8 לרשום את המסך ברישום התחומים
```js
var SCREEN_DOMAINS = { ..., xScreen: ["x"] };   // js/app.js
```
בלי זה, מחיקה שנעשתה במכשיר אחר לא תגרום למסך הפתוח להתרענן.

## 5. שני אילוצים שמעצבים כל תכנון

### 5.1 אין אינדקס מורכב
אימות דו-שלבי על `gizbar30` חוסם את קונסולת Google Cloud, ולכן **אי-אפשר
ליצור אינדקס מורכב**. כל שאילתה חייבת להיות **שאילתת שוויון בלבד** —
בלי מיון ובלי אי-שוויון — כי רק אלה נשרתות מהאינדקסים האוטומטיים
(מיזוג זיגזג). זו הסיבה ש-`budgetTx` הוא מסמך לכל תנועה עם `year`
ו-`familyId` כשדות שוויון. **אל תוסיף `orderBy` — השאילתה תיפול בייצור.**

### 5.2 אין Cloud Functions (Spark, בלי כרטיס אשראי)
אין טריגר שרץ על כתיבה ל-Firestore. כתיבה מהדפדפן מוחלת על הגיליון
בתבנית **"תיבת דואר"**: הדפדפן כותב עם `statusPending: true`, והעבודה
השעתית (`budgetTxApplyPending_`) מחילה. המשמעות: החלה מתעכבת עד שעה,
והנעילה (`withSyncLock_`) היא **מייעצת** ולא טרנזקציונית.

מכסות Spark: 50,000 קריאות ליום, ~20,000 כתיבות. כל `get()` **בתוך כלל**
נספר גם הוא.

## 6. מתי **לא** להעביר, ומה לעשות במקום
לפני שמעבירים תחום — לשאול אם בכלל צריך. שתי חלופות זולות בהרבה:

1. **לספור בעמודה אחת במקום למשוך שורות.** `countStatus_` — אם הלקוח
   צורך מספר אחד, אין סיבה לשלוח לו שורות. חסך ~3 שניות ו-9KB בעמוד
   הבית, והוריד מהחוט ת.ז. ותשובות שאלון בריאות.
2. **לאחד קריאות.** `homeExtras` מאחדת שש קריאות לאחת וחוסכת חמש
   רצפות של שתי שניות. ⚠️ אבל לבדוק שאין בתוכה קריאה כפולה לאותו
   מקור — היא קראה את יומן Google פעמיים.

## 7. איך בודקים שזה עובד
- **מסך "מצב המערכת"** (מנהל-על, אריח בתפריט המשתמש) — מדליק ומכבה כל
  דגל, ומריץ קריאת Firestore **אמיתית מהדפדפן** לכל מסמך מרכזי עם
  מדידת זמן. 🔴 הבדיקה חייבת לרוץ שם ולא בשרת: כללי האבטחה נאכפים על
  הקורא, ו-Apps Script עוקף אותם דרך חשבון שירות — בדיקה שרצה בשרת
  מצליחה **תמיד**.
- **`tools/`** — 42 מארזי בדיקה, ~1,914 בדיקות. `npm install` בתיקייה
  פעם אחת בכל מכונה חדשה (jsdom).
- לכל תחום חדש: מארז שבודק את רשימת ההיתר, את הכלל, ואת הנפילה לאחור.

## 8. סדר הפריסה — **ארבעה שערים, לא שלושה**
1. **Push** ל-GitHub (לקוח). חייב `?v=` חדש ב-`index.html` **וב-**`service-worker.js`.
2. **Apps Script** — לפריסה → ניהול הפריסות → **עיפרון** → גרסה חדשה → לפריסה.
   לעולם לא "פריסה חדשה" מהתפריט — זה יוצר URL חדש ושובר את האפליקציה.
3. **כללי Firestore** — פרסום מקונסולת Firebase.
4. **זריעה ואז הדלקה** — להריץ את פונקציית הסנכרון פעם אחת, לוודא
   שהמסמכים קיימים ונקראים, **ורק אז** להדליק את הדגל.

⚠️ הסדר אינו שרירותי: דגל שנדלק לפני שהמסמכים קיימים נותן מסך ריק.
