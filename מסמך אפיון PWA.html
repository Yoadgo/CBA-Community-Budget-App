מה תושב יראה אחרי שנעשה את זה, ומה לא ישתנה בכלל.

אייקון על המסך

התושב נכנס לאתר פעם אחת, מוסיף למסך הבית, ומאז יש לו אייקון של השיכון עם הכיתוב "קהילה" בין האפליקציות.

בלי סרגל הדפדפן

נפתח במסך מלא — בלי שורת כתובת, בלי כפתורי דפדפן. נראה ומרגיש כמו אפליקציה אמיתית.

נפתח מיד, גם בלי רשת

במקום מסך לבן של 2–3 שניות, האפליקציה מופיעה כמעט מיידית ומציגה את הנתונים האחרונים שנשמרו במכשיר.

ובהמשך — התראות

PWA הוא תנאי מוקדם. באייפון אי אפשר לשלוח התראה לאתר שלא הותקן למסך הבית — ולכן סדר השלבים כאן הוא היחיד שאפשרי.

המחיר: PWA מוסיף שכבה אחת חדשה בין הדפדפן לאפליקציה (Service Worker). היא חזקה — ואם לא מוגדרת נכון, היא יכולה "להקפיא" גרסה ישנה אצל תושבים ולגרום לך לחשוב שדיפלוי לא עבד. רוב המסמך עוסק בדיוק במניעת זה.

ב. service-worker.js — הזיכרון של האפליקציה

קובץ אחד, כ-90 שורות, בלי ספריות. שלוש משימות: התקנה (מוריד ושומר את שלד האפליקציה — index.html, 6 קבצי CSS, 21 קבצי JS, האייקונים; כ-1.2MB), הגשה (מגיש מהמטמון מיידית, עובד בלי רשת), ניקוי (מוחק מטמון ישן כשמגיעה גרסה חדשה).

ג. js/pwa.js — החיבור לאפליקציה

הקובץ היחיד שהמשתמש "מרגיש": רישום ה-Service Worker, זיהוי גרסה חדשה והטוסט, פריט ההתקנה בתפריט, שכבת ההסבר לאייפון, וחיווי "לא מקוון". משתמש ב-CBA.ui הקיים — בלי להמציא רכיב חדש.

4 אסטרטגיית המטמון — הלב של האפיון

מה נשמר במכשיר ומה לעולם לא. כאן נקבע אם המערכת תהיה אמינה או תהפוך לסיוט.

5 עדכוני גרסה — "רענון כמו שעובד בשוטף"

ההחלטה שלך כאן חסכה לנו מנגנון שלם. הנה למה.

בגרסה 1.0 הצעתי לבנות מגן חדש שיבדוק "האם המשתמש באמצע משהו". אבל בדקתי בקוד — המגן הזה כבר קיים ועובד. הפונקציה doPoll ב-js/app.js, שרצה כל 3 שניות ומרעננת נתונים מהגיליון, כבר יודעת לדלג בדיוק בכל המקרים הרגישים:

התנאי הקייםמה הוא מונע
CBA.sheets.isDirty()יש עריכה מקומית או שמירה שטרם אושרה בשרת — כולל שמירות שממתינות בתור.
userIsEditingMain()הפוקוס נמצא בתוך שדה קלט במסך הראשי — למשל תושב שממלא טופס הגשת קבלה, עוד לפני שיש בכלל מה לשמור.
document.hiddenהמשתמש בכלל לא מסתכל על האפליקציה כרגע.
מודל/דיאלוג פתוחנבדק דרך CBA.ui, בדיוק כמו היום.
המימוש שנקבע: רענון-הגרסה עובר דרך אותו שער בדיוק. ה-Service Worker מוריד את הגרסה החדשה ברקע ומרים דגל "מוכן". הרענון עצמו יקרה רק ברגע הראשון שבו כל התנאים למעלה מרוצים — כלומר בדיוק באותם רגעים שבהם המערכת כבר היום מרשה לעצמה לצייר מחדש. אפס קוד הגנה חדש, אפס התנהגות חדשה ללמוד, ואפס סיכוי לאיבוד הקלדה.
// js/pwa.js — הרעיון בקצרה
var updateReady = false;

navigator.serviceWorker.register('service-worker.js?v=20260820b')
  .then(function (reg) {
    reg.addEventListener('updatefound', function () {
      var sw = reg.installing;
      sw.addEventListener('statechange', function () {
        // גרסה חדשה מוכנה, ויש כבר גרסה פעילה = זה עדכון, לא התקנה ראשונה
        if (sw.state === 'installed' && navigator.serviceWorker.controller) {
          updateReady = true;
          sw.postMessage({ type: 'SKIP_WAITING' });
        }
      });
    });
  });

// אותו שער בדיוק שבו doPoll משתמש היום — לא ממציאים חדש
function safeToReload() {
  if (document.hidden) return false;
  if (CBA.sheets.isDirty && CBA.sheets.isDirty()) return false;
  if (CBA.userIsEditingMain && CBA.userIsEditingMain()) return false;
  if (CBA.ui.isModalOpen && CBA.ui.isModalOpen()) return false;
  return true;
}

navigator.serviceWorker.addEventListener('controllerchange', function () {
  tryReload();
});

var reloaded = false;
function tryReload() {
  if (reloaded || !updateReady) return;
  if (!safeToReload()) return;          // עסוקים — ננסה שוב במחזור הבא
  reloaded = true;
  CBA.ui.toast('עודכנה גרסה חדשה — מרעננים…');
  setTimeout(function () { location.reload(); }, 1200);
}
// נבדק שוב באותו קצב של הרענון השוטף
setInterval(tryReload, 3000);
הערת מימוש קטנה: userIsEditingMain היא היום פונקציה פרטית בתוך app.js. כדי ש-pwa.js יוכל להשתמש בה נצטרך לחשוף אותה תחת CBA — שינוי של שורה אחת, בלי לגעת בהתנהגות.

6 כפתור ההתקנה בתפריט המשתמש

המיקום שקבעת: בין "ניהול מיילים" ל"הגדרות".

הפריט נבנה ב-js/app.js, כמשתנה חדש installItem שנכנס לשרשור:

switchItem + simItem + emailItem + installItem + settingsItem + action
תנאימה מוצג
אייפון/ספארי, טרם הותקןהמקרה השכיח אצלנו. הפריט "התקנת האפליקציה" פותח את שכבת ההסבר הידנית (סעיף 7), כי ספארי לא נותן חלון התקנה.
אנדרואיד/כרום, טרם הותקןאותו פריט — הלחיצה מפעילה את חלון ההתקנה של המערכת דרך beforeinstallprompt.
כבר מותקן (רץ ב-standalone)הפריט לא מוצג כלל. אין טעם להציע התקנה למי שכבר בפנים.
דפדפן שלא תומךלא מוצג.
נסגר: הפריט יוצג בשני האזורים. באזור הניהול הוא ייפול בדיוק בין "ניהול מיילים" ל"הגדרות" כפי שביקשת; באזור התושב — שבו שני הפריטים האלה לא קיימים כלל — הוא יופיע לבדו באותו מקום ברשימה, מתחת למפריד. משבצת אחת לזכור, ושני הקהלים מקבלים אותו.

7 אייפון — הפרק שהפך למרכזי

מאחר שרוב הקהל באייפון, כל מה שספארי עושה אחרת הוא לא "מקרה קצה" אלא מסלול ברירת המחדל.

7א. ההצעה היזומה — מתי היא צצה, וכמה

אושר. זה המנגנון שיקבע כמה תושבים בכלל יתקינו — ולכן גם כמה תושבים יוכלו לקבל התראות בשלב ג'. אבל בדיוק בגלל זה הוא חייב להיות מדוד: שכבה נודניקית תגרום לאנשים לסגור מיד ולעולם לא לחזור.

הכללים המדויקים — כולם נשמרים במפתח מקומי אחד, cba_install_hint_v1:

כללהפירוט
לא בביקור הראשוןמופיעה מהביקור השני והלאה בלבד. בפעם הראשונה התושב עוד מנסה להבין מה זו האפליקציה — לא הרגע לבקש ממנו משהו.
רק אחרי כניסה מוצלחתלא מוצגת לאורח שעומד במסך הכניסה. מציעים להתקין רק למי שכבר בפנים ויודע מה הוא מתקין.
לא באמצע עבודהעוברת דרך אותו שער של סעיף 5 — לא צצה כשיש עריכה פתוחה, שדה בפוקוס או מודל פתוח. עקביות מלאה עם שאר האפליקציה.
מקסימום פעמיים בחייםמוצגת בביקור השני; אם התושב התעלם — עוד פעם אחת בערך שבוע אחר כך. ואז לעולם לא שוב. שתי הזדמנויות זה מספיק כדי שלא יפספסו, ומעט מספיק כדי שלא ירגיש כמו פרסומת.
סגירה = הפסקהסגירה רגילה מקפיצה לשבוע הבא. "אל תציגו לי שוב" מכבה לצמיתות, ומייד.
נעלמת מעצמהברגע שזוהה שהאפליקציה מותקנת (רצה ב-standalone), המנגנון כבוי לגמרי — כולל פריט ההתקנה בתפריט.
הצורה: לא מודל שחוסם. פס שקט שנכנס מלמטה — אייקון קטן, שורה אחת: "אפשר לשמור את קהילה על מסך הבית", כפתור "איך?" וכפתור סגירה. לחיצה על "איך?" היא שפותחת את שכבת ההסבר המלאה. כך התושב שלא מעוניין מפטר את זה בתנועה אחת, והמעוניין מקבל את ההסבר המלא.
נקודה שכדאי לדעת מראש: באנדרואיד הדפדפן ממילא מציג באנר התקנה משלו. אצלנו הפס יוצג בעיקר לתושבי אייפון — בדיוק הקהל שבלעדיו לא היה יודע שהאפשרות קיימת. זה מדויק ולא מקרי.

7ב. שכבת ההסבר — מאוירת, בלי צילומי מסך

ספארי לא נותן שום כפתור התקנה אוטומטי, ולכן ההסבר הזה הוא הרכיב שיקבע אם הפרויקט יצליח.

  1. שכבה שעולה מלמטה, על בסיס ה-Drawer הקיים — לא חלון חדש.
  2. שלושה שלבים, כל אחד עם איור SVG שנצייר בעצמנו בקו נקי בשפת האפליקציה: (א) סמל השיתוף של אפל — ריבוע עם חץ כלפי מעלה; (ב) שורת "הוספה למסך הבית" — ריבוע עם פלוס; (ג) אייקון "קהילה" יושב על מסך בית.
  3. כפתור סגירה, וכפתור "אל תציגו לי שוב".
  4. משפט אחרון, קטן יותר: "בפתיחה הראשונה מהאייקון תתבקשו להתחבר שוב — זה תקין." — מטפל מראש במלכודת האחסון הנפרד.
יתרון שלא צפינו: ההחלטה לוותר על צילומי מסך יצאה טובה יותר, לא רק פשוטה יותר. צילום מסך מאייפון מזדקן — אפל משנה את תפריט השיתוף כמעט בכל גרסה, והצילום שלנו יהפוך לשגוי בלי שנשים לב, ובדיוק ברכיב הכי רגיש. איור בקו נקי של הסמלים עצמם (הם לא משתנים) יישאר מדויק לאורך שנים, ייטען מיידית כי הוא חלק מהקוד, ויתאים לשפת העיצוב במקום להתנגש איתה. גם החיסכון אמיתי: אלה 3 איורים קטנים שנכתבים ישירות בקוד, בלי קבצי תמונה בכלל.

9 התראות Push — אפיון ביצועי (מאושר, Cloudflare)

הכיוון אושר. הפרק הזה הוא כבר לא "האם" אלא "איך" — כולל הארכיטקטורה המדויקת.

למה Cloudflare ולא Firebase

Apps Script אינו יכול לשלוח Web Push לבד — התקן דורש חתימת ECDSA P-256 (VAPID), ו-Apps Script לא מספק אותה. זו מגבלה קשיחה. Firebase היה עוקף אותה, אבל במחיר ספריית JavaScript חיצונית באפליקציה — בניגוד ישיר לכלל "HTML/CSS/JS טהורים בלבד". Cloudflare Worker שומר על האפליקציה נקייה לחלוטין: בצד הלקוח משתמשים רק ב-API שמובנה בכל דפדפן, בלי אף ספרייה.

הארכיטקטורה — מי מדבר עם מי

  1. התושב מאשר. לוחץ "הפעל התראות" במסך ההעדפות. הדפדפן מייצר "כתובת מנוי" ייחודית למכשיר הזה.
  2. המנוי נשמר בגיליון. האפליקציה שולחת אותו ל-Apps Script, שרושם שורה בטאב "מנויי התראות".
  3. אירוע קורה. גזבר מאשר בקשת החזר. Code.gs כבר קורא היום ל-sendResidentTemplate_ לשליחת מייל — נוסיף לידה קריאה ל-sendPush_.
  4. Apps Script פונה ל-Worker. שולח לו בבקשה אחת: את המנוי, את הכותרת, את הטקסט — יחד עם סוד משותף שמאמת שהבקשה באמת מאיתנו.
  5. ה-Worker חותם ושולח. מייצר חתימת VAPID ומעביר את ההתראה לשרת הדחיפה של אפל/גוגל.
  6. ההתראה מגיעה. ה-Service Worker במכשיר מקבל אותה ומציג אותה. לחיצה פותחת את האפליקציה ישירות במסך הרלוונטי.

עיקרון מנחה: Push לא מחליף את המייל — הוא מקדים אותו. אותו אירוע, אותה תבנית תוכן מטאב "הגדרות מיילים", שני ערוצים. כך אין מנגנון שני להחזיק, ותושב בלי התראות לא מפספס כלום. תבנית מייל קיימת = שורת Push אפשרית, בלי קוד חדש לכל אירוע.
שליטה של המשתמש: ההרשאה מתבקשת רק אחרי לחיצה יזומה של התושב — לעולם לא בפתיחת האפליקציה. בקשת הרשאה מיידית = כ-70% דחייה, ובאייפון אי אפשר לבקש שוב אחרי סירוב.
הרשאות: שליחת Push יזומה (למשל "הודעה לכל התושבים") היא פעולת ניהול — תיכנס ל-ACTION_PERMS הקיים כפעולה חדשה, לא כבדיקה עצמאית.
תלות מוחלטת: באייפון, Push עובד אך ורק אחרי שהאפליקציה הותקנה למסך הבית. תושב שלא התקין לא יקבל שום התראה — ולא נוכל אפילו לבקש ממנו הרשאה. לכן הצלחת שלב ג' תלויה ישירות בכמה תושבים באמת יתקינו בשלבים א'–ב'. זו סיבה נוספת להשקיע בשכבת ההסבר של סעיף 7.
